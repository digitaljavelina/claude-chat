## Summary

Phase 2 is pure orchestration, not engineering. The hard technical work — atomic file writes, clobber defense, YAML frontmatter emission, JSONL parsing — is done in Phase 1's `sync_chats.py`. Phase 2's job is to author a SKILL.md that acts as a Bash + markdown orchestrator: it calls `sync_chats.py scan` to get the work queue, reads session JSONL files to extract message context, prompts Claude (itself, in-session) for a label, extracts the JSON from Claude's response, and pipes it to `sync_chats.py write`. The entire AI labeling path is exactly one Bash invocation plus one regex per session.

The unusual aspect of this phase is the in-session model invocation: there is no external API call. The skill's "prompt" is markdown text that Claude reads as part of executing the skill. Claude is simultaneously the skill executor and the labeler. This is architecturally clean but must be understood clearly when writing the skill — particularly when structuring the label prompt, since it must cause Claude to emit a `\`\`\`json` fenced code block as output that the skill can then extract.

The SKILL.md frontmatter for this skill needs three non-standard fields compared to simple skills like `daily`: `disable-model-invocation: true` (Phase 2 uses in-session Claude, not a separate model invocation), `allowed-tools: [Bash, Read]` (whitelist — no Write tool, all vault writes go through `sync_chats.py`), and `argument-hint` (documentation for the slash command).

**Primary recommendation:** Write the SKILL.md as a sequentially-executed instruction document. Keep the looping logic in numbered steps. Trust the Phase 1 pipeline completely — the skill's only job is to assemble the right label JSON and pipe it in.

### The In-Session Labeling Pattern

This is the core architectural insight of Phase 2: Claude is both the skill executor and the labeler. When the skill says "now generate a label for this session", Claude generates it inline as part of executing the skill. The skill does not make any API call or invoke a subprocess to Claude — it simply presents the extracted messages and the labeling prompt as text, and Claude's response (which the skill then reads back and processes) contains the label.

The mechanism:

1. Skill uses `Read` tool to load JSONL file
2. Skill extracts first N + last N user/assistant messages (as text in the skill's response)
3. Skill presents the label prompt inline, including the extracted messages
4. Claude produces a response containing a `\`\`\`json` block
5. Skill uses `Bash` tool with a Python one-liner to extract the JSON from the last response

Step 5 is the trickiest: the skill needs a way to capture what Claude just output. In practice, this means the skill's instructions must tell Claude to emit the label in a fenced code block, and then the skill either (a) has Claude self-extract it using the `Bash` tool with `echo` + the label it just produced, or (b) the planner structures the skill so the label generation and extraction are in the same logical step and Claude pastes the extracted JSON directly into the Bash command.

**Recommended approach (Claude's Discretion area):** Have Claude generate the label, then immediately emit a Python one-liner that constructs the exact echo command:

```bash
echo '{"title":"...","gist":"...","tags":["..."],"coherence_score":4,"needs_review":false}' | python3 ~/.claude-chat/sync_chats.py write <session_id>
```

Claude fills in the JSON values from the label it just generated. This avoids needing to capture Claude's output programmatically — Claude builds the pipe command directly. [ASSUMED: this pattern is inferred from how skills execute; no official documentation describes this exact flow]

- CONTEXT.md D-05: "user message count < 2"

### Anti-Patterns to Avoid

- **Writing vault files directly from the skill.** The `Write` tool is NOT in the `allowed-tools` whitelist by design (D-09). All writes go through `sync_chats.py write` stdin pipe. The clobber defenses only exist in `cmd_write`.
- **Retrying failed label generation.** D-08 is explicit: one failure = one stub, no retry, no latency doubling.
- **Hardcoding `~` as a literal tilde in Bash.** Use `$HOME` in Bash commands — `~` is shell-expanded by the interactive shell but may not be inside `Bash` tool calls depending on how they are invoked.
- **Attempting to parse the full JSONL in Python in-skill for every session.** Extract only the needed messages; sessions can be large. The skill should read the `path` from the scan output and pass it to either the Read tool or a targeted Bash one-liner.
- **Assuming `sync_chats.py` is on PATH.** It lives at `~/.claude-chat/sync_chats.py` (or `$HOME/.claude-chat/sync_chats.py`). Always invoke as `python3 $HOME/.claude-chat/sync_chats.py <subcommand>`.

## Common Pitfalls

### Pitfall 1: Shell Quoting in the Echo Pipe

**What goes wrong:** The label JSON will contain apostrophes, quotes, and special characters (titles like "Michael's homelab" or gists with quoted text). A naive `echo '...' | python3 ...` will break on single quotes inside the JSON.

**Why it happens:** Shell single-quote strings cannot contain literal single quotes. A title like `Fix user's login issue` breaks `echo '{"title":"Fix user's login issue"}'`.

**How to avoid:** Use Python's `json.dumps()` to serialize the label dict (which escapes correctly), then use `printf '%s'` or a Python heredoc approach. The cleanest pattern is to have Claude write the label JSON to a temp file and pipe from the file:

```bash
python3 -c "import json; print(json.dumps({'title':'...','gist':'...','tags':[...],'coherence_score':4,'needs_review':False}))" | python3 $HOME/.claude-chat/sync_chats.py write <session_id>
```

Claude fills in the Python dict literal, and `json.dumps` handles all escaping.

**Warning signs:** `Unexpected token` or `unterminated string` errors from `sync_chats.py write`.

### Pitfall 2: Confusing `disable-model-invocation: true` with "Claude can't think"

**What goes wrong:** The `disable-model-invocation` frontmatter field sounds like it disables AI entirely. It does not. It disables Claude Code from making a _separate_ model API call when the skill is loaded. Claude is still the in-session executor — it reads the skill and acts. Phase 2 relies on Claude being active; `disable-model-invocation: true` just means "don't spawn an additional model call for this skill's context."

**Why it happens:** The field name is counterintuitive. The `daily` skill does not have it, and that skill uses Claude's understanding too.

**How to avoid:** Keep `disable-model-invocation: true` as decided (D-09). Document this in SKILL.md with a comment explaining it means no extra API call, not no AI.

**Warning signs:** N/A — this is a misread of documentation, not a runtime error.

### Pitfall 3: Session Path in Scan Output is Absolute

**What goes wrong:** The `path` field in `sync_chats.py scan` output is an absolute path string (e.g., `/Users/michaelhenry/.claude/projects/...`). Using the `Read` tool with a relative path or a shell `~` expansion fails.

**Why it happens:** `str(f)` in `discover_sessions()` at line 227 serializes `pathlib.Path` as an absolute string. [VERIFIED: line 227 of sync_chats.py]

**How to avoid:** Use the `path` value from the scan JSON directly in `Read` tool calls and Bash commands. No expansion needed — it's already absolute.

### Pitfall 4: JSONL Files Can Have Tool-Call-Only Lines

**What goes wrong:** A session with high tool call volume may have many lines where `role == "assistant"` and `content` is a list of `{"type": "tool_use", ...}` blocks — no text. Extracting "assistant messages" naively yields empty strings.

**Why it happens:** Claude's JSONL format includes all event types, including tool invocations. The `extract_first_user_message` function already filters these (skips non-text content). The Phase 2 message extraction must do the same.

**How to avoid:** When extracting first+last N message pairs for the labeling prompt, filter to lines where the text content is non-empty after stripping tool-use blocks. [VERIFIED: `extract_first_user_message()` at line 283 demonstrates the filtering pattern]

### Pitfall 5: `$ARGUMENTS` is Empty for No-Argument Skills

**What goes wrong:** SKILL.md templates that reference `$ARGUMENTS` will get an empty string when `/sync-chats` is invoked with no arguments (which is the only invocation mode per D-10).

**Why it happens:** `$ARGUMENTS` is the skill's argument placeholder. When a skill accepts no arguments, this variable is empty.

**How to avoid:** Do not reference `$ARGUMENTS` in the sync-chats SKILL.md body at all. The skill has no arguments to process.

### Pitfall 6: ~/ vs $HOME in Bash Tool Calls

**What goes wrong:** Bash one-liners in skill instructions that use `~` for home directory expansion may fail if the shell invoked by the `Bash` tool does not expand `~` in the same context.

**How to avoid:** Use `$HOME` everywhere in the skill's Bash commands. `$HOME` is an environment variable that is reliably set in all shell contexts. [ASSUMED: based on standard shell behavior; `$HOME` is universally safer than `~` in non-interactive contexts]

### User Message Count (ultra-short skip check)

```bash
# Count user messages in a JSONL file
USER_MSG_COUNT=$(python3 -c "
import json, sys
path = '$SESSION_PATH'
count = 0
with open(path, encoding='utf-8', errors='replace') as f:
    for line in f:
        try:
            obj = json.loads(line.strip())
            msg = obj.get('message', obj)
            if msg.get('role') == 'user':
                content = msg.get('content', '')
                if isinstance(content, str) and content.strip():
                    count += 1
                elif isinstance(content, list):
                    for b in content:
                        if isinstance(b, dict) and b.get('type') == 'text' and b.get('text','').strip():
                            count += 1
                            break
        except Exception:
            pass
print(count)
")
```

### JSON Code Block Extraction Regex (Python)

````python
import re, json

def extract_label_json(response_text):
    """Extract the first ```json code block from Claude's response."""
    match = re.search(r'```json\s*(.*?)\s*```', response_text, re.DOTALL)
    if not match:
        return None
    try:
        return json.loads(match.group(1))
    except json.JSONDecodeError:
        return None
````

## Open Questions

1. **Does `disable-model-invocation: true` block in-session AI use?**
   - What we know: The field exists in D-09 and the CONTEXT.md. The `daily` skill does NOT have it. The `gsd-do` skill does NOT have it.
   - What's unclear: The exact semantics — does it prevent ALL model invocation including in-session, or only prevent an _additional_ model call when the skill is loaded?
   - Recommendation: The planner should include a Wave 0 verification step: create a minimal SKILL.md with `disable-model-invocation: true` and confirm it can still perform AI reasoning inline. If it blocks all AI use, remove this flag. The CONTEXT.md D-09 says "Phase 2 uses Claude in-session, not a separate model call" — which implies in-session AI still works.

2. **How does the skill capture Claude's label output for the Bash pipe?**
   - What we know: Claude generates a `\`\`\`json`block in its response. The skill then needs to pipe this to`sync_chats.py write`.
   - What's unclear: The exact mechanism by which Claude's in-skill output becomes the input to a subsequent Bash command. Claude can write Bash commands with the values filled in, or use a temp file approach.
   - Recommendation: Instruct Claude to construct the complete Bash command (with all label values inlined) as part of generating the label. This is the most robust approach. The planner should document this instruction pattern explicitly in the SKILL.md template.

3. **Phase 1 completion status**
